# FFI 绑定技术方案评估

> **只读文档。** 本文是技术选型的决策记录，不随后续开发修改。
> 所有数字来自对厂商原始包的实测，不是估算。

---

## 一、背景数据（实测）

### 1.1 两家头文件规模

| | 大华 `dhnetsdk.h` | 海康 `HCNetSDK.h` | 合计 |
|---|---|---|---|
| 文件大小 | 8.57 MB | 2.55 MB | 11.1 MB |
| 行数 | 169314 | 52934 | 222248 |
| 函数 | 2528 | 948 | **3476** |
| `typedef struct` | 10531 | 2501 | **13032** |
| 默认参数 `= NULL/0` | 37 | **210** | 247 |
| 引用参数 `&` | 1 | **76** | 77 |
| `extern "C"` | 2 | 2 | 4 |

海康那 210 处默认参数和 76 处引用参数，对 C 解析器（ctypesgen / pycparser）是语法错误，
对 C++ 编译器是合法语法。这一条直接影响方案选择。

### 1.2 海康侧两个关键事实

**海康提供 `.lib`，pybind11 / Cython / CFFI-API 的链接前提成立：**

```
库文件\HCNetSDK.lib        211 KB
库文件\HCCore.lib          307 KB
库文件\PlayCtrl.lib        175 KB
库文件\HCNetSDKCom\HCAlarm.lib / HCGeneralCfgMgr.lib / HCPreview.lib
```

**海康的 Python 示例是 Demo 级碎片，不能当 SDK 用：**
`Demo示例\5- Python开发示例\` 下 7 个子目录，每个各带一份 `HCNetSDK.py` 副本，
最大的一份（参数配置）：**1109 行 / 51 结构体 / 71 函数**，
`argtypes` 0 处、`restype` 0 处、无类封装 —— 够跑那个 Demo 就完事。

### 1.3 大华 wheel 的覆盖水平（行业参照）

大华官方 Python wheel：1400 结构体 + 272 方法。
即：**厂商自己也没做到全量**（对比 10531 / 2528）。

### 1.4 规模推导

按"覆盖到官方 SDK 水平"（大华 1400 结构体、平均约 9 字段）估算胶水代码量：

```
1400 × 9   ≈ 12600 行    大华结构体
2501 × 9   ≈ 22500 行    海康结构体
3476                      函数
──────────────────────────
≈ 3.8 万行
```

## 二、前提：AI 承担手写成本

"AI 写代码不累"这一条，把最大的成本项（3.8 万行手写胶水）归零了。
成本项因此重新排序：

1. 布局正确性
2. 编译成本（AI 秒写，MSVC 慢慢编）
3. 分发复杂度

---

## 三、先砍掉一个伪指标：性能

这类 SDK 调用全是网络 I/O，单次耗时毫秒到秒级。

| 调用方式 | 单次开销 |
|---|---|
| ctypes | ~1–2 μs |
| pybind11 / Cython | ~0.1 μs |

差 10 倍，但在毫秒级 I/O 面前占比约 0.01%。**"pybind11 更快"在本场景价值约等于零，不应影响决策。**

唯一例外是码流回调（每秒 25–50 次），但回调体通常只是 memcpy，也不是瓶颈。

---

## 四、真正决定胜负的三件事

### 1. 布局正确性（最重要）

结构体字段的偏移/大小，是"编译器算出来的"还是"人/解析器描述的"。
这是这类项目唯一的硬伤来源 —— 一个字段宽度算错，就是运行时静默错位，且无自动发现机制。

### 2. 编译成本

3.8 万行胶水是小时级，且若胶水集中在单个 TU，改一行就全量重编。
**缓解手段：按模块拆分成多个 `.cpp`（如 50 个），让增量编译生效。**

### 3. 分发

- 纯 Python：一个 zip 通吃所有 Python 版本
- 编译产物：需按 Python 版本出 wheel，除非走稳定 ABI（abi3）

## 五、全谱评估

| 方案 | 布局正确性 | 编译成本 | 迭代 | 分发 | 换 SDK 版本 |
|---|---|---|---|---|---|
| **ctypes**（生成/手写） | ❌ 靠解析器或 AI 描述，错了不报错 | **0** | 秒级 | 纯 py | 重跑 |
| **CFFI ABI** | ❌ 同上 | **0** | 秒级 | 纯 py | 重跑 |
| **CFFI API** | ✅ C 编译器兜底 | 中（C） | 分钟 | 编译 / abi3 | 改 cdef |
| **Cython** | ✅ C 编译器兜底 | 低（出 C 代码） | 分钟 | 编译 / 有限 abi3 | 改 .pxd |
| **pybind11** | ✅ 编译器兜底 | **高**（C++ 模板，规模一大即爆炸） | 慢 | ✅ abi3 成熟 | 改胶水 |
| **nanobind** | ✅ 编译器兜底 | **低**（专为压编译时间设计，比 pybind11 快 2–4×，产物小 ~70%） | 中 | ✅ 稳定 ABI | 改胶水 |
| **SWIG** | ✅ 编译器兜底 + **唯一自带全量自动化设计** | 中 | 中 | 编译 | 喂新头文件重跑 |
| **cppyy** | ✅ Clang 保证 | **0**（运行时解析，不编译） | 秒级 | 纯 py + Clang 依赖 | 自动 |
| **PDB 真值表 + ctypes**（hybrid） | ✅ 编译器 PDB 是权威数据 | 0（只编一个空 .obj 取 PDB） | 秒级 | 纯 py | 重跑 |

## 六、三个值得进候选的补充方案

### cppyy

用 Clang 在运行时解析头文件，自动生成绑定。
零手写、零编译、全量覆盖、布局由 Clang 保证 —— 理论上最贴合本场景。

**风险**：Windows 生态弱于 Linux（官方主要经 conda 分发），首次解析有启动开销，出错时调试链路长。
值得花半天验证，不行就放弃。

### SWIG

老，但它是唯一为"给我头文件，我还你全套绑定"而设计的。`%include "HCNetSDK.h"` 一行全吃。
代价：产物代码丑、现代 C++ 特性支持有坑、Windows 工具链需自行配置。

### PDB 真值表（hybrid，最具性价比）

编一个只含 `#include "HCNetSDK.h"` 的空 `.cpp`，用 `/Zi` 产出 PDB，
**从调试信息里直接读出每个结构体的字段名、偏移、大小** —— 编译器自己算的，100% 准确。

然后二选一：
- 用它**生成** ctypes 声明
- 用它**校验** AI 写的 ctypes 声明

同时拿到"编译器的正确性"和"ctypes 的零编译 / 秒级迭代 / 纯 Python 分发"。
唯一门槛：需要解 PDB（DIA SDK via `comtypes`，或 `pdbparse`）。

## 七、结论排序

**第一梯队：nanobind**
编译器兜底 + 编译快 + 产物小 + 可生成 `.pyi` 存根（13000 个结构体的 IDE 补全，
这是 ctypes 那个 11MB 文件根本做不到的）+ 稳定 ABI 一次编译全版本通用。
它存在的理由就是"pybind11 编译太慢"。

**第二梯队：Cython**
出 C 而非 C++ 模板，在 3.8 万行量级上编译可能比 nanobind 还快。生态成熟、文档全。
代价：`.pxd` 语法偏老、补全体验一般。

**不建议：pybind11**
在本规模上编译最慢（模板实例化爆炸），而它的生态优势（资料多）意义不大 —— 反正代码是 AI 写的。

**不建议：ctypes 系**
除非走 PDB 校验那条路。没有编译器兜底，AI 写 13000 个结构体字段，
错一个偏移就是运行时静默错位，且没有任何机制能自动发现。

---

## 八、推荐组合

> **nanobind 做主体** + **PDB 真值表做回归校验**

前者保证日常开发体验与分发；后者在换 SDK 版本时自动比对新旧布局差异
（`sizeof` / `offsetof` 一比，哪家改了结构体立刻可见）。

这套组合把"AI 批量产出"的唯一风险点 —— 静默正确性 —— 堵死了。

## 九、下一步实验

两个并行小实验，均在独立目录进行，不触碰现有代码：

1. **nanobind 编译实测**
   绑定 `NET_DVR_TIME` + `NET_DVR_Init` + `NET_DVR_GetLastError`，链接 `HCNetSDK.lib`。
   测出「单结构体编译耗时」与「产物体积」，据此外推 3.8 万行的真实耗时。
   **这个数字决定一切。**

2. **PDB 真值表可行性**
   编一个空 `.cpp` 取 PDB，验证能否用 Python 读出结构体布局。
